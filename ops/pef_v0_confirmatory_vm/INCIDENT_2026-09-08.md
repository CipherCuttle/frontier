## Incident evidence

### 1. Incorrect pooled endpoint for a session advisory lock

The deployed canonical credential used Neon's transaction-pooled `-pooler` endpoint while `PostgresWorkerLease` uses session-level `pg_try_advisory_lock` / `pg_advisory_unlock` semantics.

Observed symptoms:

- successful cycles logged `worker lease release failed: lock not held`;
- Neon inspection found the exact FRONTIER advisory lock stranded on a backend whose `application_name` was `pgbouncer`;
- a direct-host lock probe initially could not acquire the lock while that pooled backend retained it.

Operational recovery performed without exposing credentials:

1. stop the worker;
2. allow the leaked pooled backend lock to disappear;
3. prove direct-host advisory lock acquire/release returns `True / True`;
4. replace only the hostname in `/etc/frontier/frontier_database_url` from pooled to direct, preserving a root-only backup;
5. restart and prove the worker's advisory lock is held on a non-PgBouncer backend session.

The direct endpoint is the correct operational configuration for this locking model.

### 2. Memory pressure and OOM were caused by the frozen implementation

The original service envelope used:

- `MemoryHigh=1800M`
- `MemoryMax=2500M`

`MemoryHigh` caused prolonged kernel throttling. The experiment thread was observed in `mem_cgroup_handle_over_high`, with stale scientific heartbeat and no forward progress.

After temporarily setting runtime `MemoryHigh=infinity`, the kernel repeatedly killed the FRONTIER Python worker at the exact cgroup hard limit. Kernel evidence showed approximately 2.55 GiB anonymous RSS in the FRONTIER service cgroup at each kill; no other host process had comparable memory use.

### 3. Frozen grouping semantics are quadratic in the retained evidence universe

`build_grouping_projection()` evaluates every unordered observation pair and retains every `AMBIGUOUS` pair in `GroupingProjection.ambiguous_pairs`.

Observed source-universe growth:

| boundary | observations | unordered pairs |
|---|---:|---:|
| 15:00 | 899 | 403,651 |
| 15:25 | 1,421 | 1,008,910 |
| 15:40 | 1,657 | 1,371,996 |
| 15:50 | 1,679 | 1,408,681 |
| ~19:40 incident corpus | 2,425 | 2,939,100 |

The 2,425-observation corpus contained only about 1.6 MiB of raw payload data; payload size is not the cause.

A temporary isolated GitHub benchmark against the exact frozen grouping implementation used 2,425 same-day low-overlap observations and produced:

- 2,939,100 pairs;
- 2,939,100 ambiguous-pair records;
- grouping projection alone: peak RSS `785,936 kB`;
- wall time about `56.82 s`.

A second benchmark continued through the exact frozen `baseline_input_digest()` canonicalization path and produced:

- the same 2,939,100 ambiguous pairs;
- peak RSS `3,457,236 kB` (~3.30 GiB);
- wall time about `78.41 s`.

This reproduces and explains the live 2.5 GiB OOM: `baseline_input_digest()` expands `grouping_projection.to_canonical()` into millions of Python dict/list objects while the already-large projection remains resident.

### 4. Hardware-only scaling is not a viable 28-day remedy

From 15:50 to about 19:40 the frozen-source universe grew from 1,679 to 2,425 observations: +746 in 230 minutes (~194.6 observations/hour). A simple linear scale stress test (not a scientific forecast) yields roughly 128,531 observations after another 27 days, or ~8.26 billion unordered pairs.

Because the frozen grouping output explicitly materializes ambiguous pair records, both time and output volume scale quadratically. Raising RAM can postpone failure but cannot make the fixed 28-day implementation operationally viable.
